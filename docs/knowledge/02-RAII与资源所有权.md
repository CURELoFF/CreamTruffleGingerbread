# 02 · RAII 与资源所有权

> 上下文：本文是模块拆分实战前的理论垫底。看完本文你要能回答：
> **资源（Resource）到底指什么？谁来负责归还？异常/提前 return 出现时，归还还能发生吗？**
> 我们即将用这套思想封装 SDL 窗口，写第一个真正"像框架"的类。

---

## 一、先想清楚问题本身：资源与所有权

**资源 (Resource)** = 从系统/环境借来的、**用完必须还**的东西：

| 我们项目里已经出现的资源 | "借"的写法 | "还"的写法 |
| --- | --- | --- |
| SDL 视频子系统 | `SDL_Init(...)` | `SDL_Quit()` |
| 一个 OS 窗口 | `SDL_CreateWindow(...)` | `SDL_DestroyWindow(window)` |
| （将来）纹理、音频设备、文件句柄、这块显存 | 各自有各自的 acquire | 各自有各自的 release |

**所有权 (Ownership)** = "这个资源由谁负责还"的回答方式。

没有明确所有权的系统，结局必然是以下两种之一：

```text
泄漏 (Leak):   借了忘了还 → 窗口句柄残留、显存吃满、最终崩溃
重复释放:  人人都以为不是自己还 → 同一资源还两次 → 立即崩溃
```

C++ 程序员的手动管理，就是维护一份**人肉对照表**：`SDL_CreateWindow` 必配 `SDL_DestroyWindow`，程序员靠自觉和 review 保证一一对应。窗口一多、退出路径一多，对照表就会烂掉。

## 二、C++ 的拆解答案：析构函数与作用域

C++ 提供了一个别人语言少有的利器——**每个对象必须在离开作用域时执行析构函数 (Destructor)**，且由编译器自动执行：

```cpp
void demo() {
    int i = 1;                    // 构造
    {
        Window w;                 // { 在构造时向系统要资源
        step1();                  // ... 使用 ...
        step2();                  // ... 无论发生什么 ...
    }                             // } 离开作用域 → w.~Window() 自动执行 → 资源归还
    // 此处 w 已不存在，任何代码都无法误用它
}
```

结晶成一句话：

> **RAII（Resource Acquisition Is Initialization，资源获取即初始化）**
> **在构造函数中获取资源，在析构函数中释放资源。**
> 于是"归不归还"不再取决于你的自觉，而取决于**作用域的边界**，而作用域边界是编译器可见的、确定的。

这名字缩写看着绕，实际含义朴素：**"拿资源"这个动作写在"出生"（构造函数）里，"还资源"写在"死亡"（析构函数）里**，由编译器把两头锁死。

## 三、为什么手动管理撑不住？两个用例

### 用例 1：多分支退出路径

```cpp
// 手动管理的日常: 每条退出路都要记得还
SDL_Window* window = SDL_CreateWindow(...);
if (!doSetup1()) { SDL_DestroyWindow(window); return; }
if (doSetup2() 返回失败) { SDL_DestroyWindow(window); return; }
...
正常路径走到底，末尾也调 SDL_DestroyWindow(window);
```
退出路径有 10 条，就得写 10 次"还"。漏一次 = 泄漏。

### 用例 2：异常 (Exception) —— 手动管理的终极杀手

```cpp
void f() {
    SDL_Window* window = SDL_CreateWindow(...);
    riskyFunc();               // 如果这里抛出异常...
    SDL_DestroyWindow(window); // ← 这行永远执行不到，资源泄漏
}
```

异常 throws 时，**从函数体"跳过"后面所有语句直达调用方**。手动调用的 release 语句被跳过。而 **RAII 类的析构函数照样会执行**——因为栈展开 (Stack Unwinding) 时，编译器会"顺路"销毁所有已经活着的局部对象。这是 RAII 与异常天然契合、而手动管理永久残疾的根本原因。

### 对比表（本课核心表格 📋）

| 问题 | 手动 release 调用 | RAII |
| --- | --- | --- |
| 正常走到尾 | ✅ 记得还就行 | ✅ 析构函数自动跑 |
| 提前 return 多分支 | ⚠️ 每条路都要记得还 | ✅ 只要出作用域必还 |
| 中途抛异常 | ❌ release 被跳过 → 泄漏 | ✅ 栈展开时析构自动跑 |
| 可读性 | 满地寻找与 acquire 一一对应的 release | 看 类定义 与 生命周期即可 |

## 四、RAII 类的最小模板（我们马上要写的就是这个）

```cpp
class Window {
public:
    // 构造 = 拿资源
    explicit Window(const char* title, int w, int h) {
        window = SDL_CreateWindow(title, w, h, SDL_WINDOW_RESIZABLE);
        if (!window) throw ...;   // 拿不到就抛错，对象"出生失败"
    }

    ~Window() {
        // 析构 = 还资源
        if (window) SDL_DestroyWindow(window);
    }

    // (还有两条规则要讨论: 拷贝/移动 —— 见下)
private:
    SDL_Window* window = nullptr;
};
```

从此使用方变成这样（对比一下手动版本）：

```cpp
int main() {
    Window win("title", 800, 600);   // 拿
    // ... 使用 ...
    return 0;                        // 出作用域自动还，异常/return 一视同仁
}
```

## 五、必须提防的坑：拷贝会让所有权模糊

窗口只有一个实体，如果允许"拷贝"这个 RAII 对象：

```cpp
Window a("窗口甲", 800, 600);
Window b = a;   // 看似无害的拷贝 → b 也试图拥有同一个窗口?
// 默认拷贝是"按位复制字段" → a 和 b 各持有一个相同指针
// 作用域结束时 a、b 都析构 → SDL_DestroyWindow 同一个窗口跑两次 → 崩溃
```

> **现代 C++ 惯例**：对"独占资源"的 RAII 类，**禁用拷贝**（把 `= delete` 写在拷贝构造/拷贝赋值上），最多允许**移动 (Move)**（"所有权转移"等同于搬家，搬走后原对象变空壳）。
> 本课程先到这里，移动语义在后续窗口类的实战中再手把手讲。
> (标准库的 `std::unique_ptr` 就是"通用版独占 RAII"，我们以后会与手写版互相印证)

## 六、概念词典

| 术语 | 一句话解释 |
| --- | --- |
| **RAII** | 构造拿资源、析构还资源，用作用域代替自觉的资源管理模式 |
| **析构函数 (Destructor, `~T()`)** | 对象死亡前编译器必调的函数，写"还资源"的地方 |
| **作用域 (Scope)** | `{}` 包围的世界，离开它 = 局部对象死亡 |
| **栈展开 (Stack Unwinding)** | 异常抛出时，沿途所有活着局部对象依次析构的过程 |
| **所有权 (Ownership)** | "谁负责还"的分析框架；独占 = 一人还 |
| **拷贝语义 (Copy Semantics)** | 按位复制成员。RAII 类默认拷贝 = 两个对象持同一资源 = 双重释放 = 崩溃 |
| **`= delete`** | 显式禁止某个函数被调用（禁拷贝的标准否决写法） |
| **移动 (Move)** | 所有权的"转账"：新对象接管资源，旧对象变成空壳 |

## 七、本篇记忆锚点 🎯

> **资源问题不是一个"memory leak 检查"问题，而是"所有权不明确"问题。**
> RAII 的看法：把资源的"借"绑定到对象的出生，"还"绑定到对象的死亡（析构），剩下的交给 C++ 作用域规程自动执行。
> **有明确的所有者 + 生命周期靠作用域说话 = 异常、多分支退出、后期维护都动摇不了这份确定性。**
