# 19 · 图层与渲染排序：谁盖住谁

> 前置：16 号（取哪一格）+ 17 号（什么时候换格）+ 18 号（布局从哪读）+ 10 号（帧循环）。
> 本文回答一个正在你代码里发生的问题：**`worldObjects` 里现在有玩家和敌人，绘制顺序就是插入顺序——敌人永远盖住玩家，不管它站在玩家上面还是下面。**

---

## 一、这是什么

### 1.1 先看现在的 bug

当前 `Application::Run()` 的绘制段长这样：

```cpp
for (const auto& e : worldObjects) {
    e->Draw(renderer_.Get(), interpolation);
}
```

没有任何排序。于是：

```text
插入顺序：player → enemy
绘制顺序：player → enemy
结果：    敌人永远画在玩家之上
```

玩家走到敌人**上方**（屏幕 y 更小、离镜头更远）时，正确画面应该是玩家被敌人遮住；玩家走到敌人**下方**（离镜头更近）时，应该是敌人被玩家遮住。现在两种情况的画面一模一样——**深度信息完全丢失了**。

### 1.2 画家算法（Painter's Algorithm）

2D 渲染没有深度缓冲，`SDL_RenderTexture` 也没有 `z` 参数。唯一的深度线索就是**画的顺序**：

> 先画远的，后画近的。后画的像素覆盖先画的像素。

这就是画家算法：像油画一样，从背景一层层往上堆。

```text
  ① 地面        floor
  ② 血迹/阴影    decal       ← 贴在地面上，但要在地面之上
  ③ 道具        item        ← 掉在地上的东西
  ④ 角色/敌人    actor       ← 这一层内部还要按 y 排序
  ⑤ 墙顶/树冠    overhead    ← 会挡住角色的上半身
  ⑥ UI / HUD    ui          ← 永远在最上
```

**注意①~③和⑤~⑥是"硬层"**：它们的先后顺序是设计规定，与时间、位置无关，不该被排序打乱。**只有④内部需要排序**。把这两件事混成一次排序，是新手最常犯的错（见 §五）。

### 1.3 3/4 俯视角的深度 = 脚底 y

你选的是 top-down + 3/4 视角（RPG Maker 风）。这种视角里，屏幕 y 就是深度的替代品：

```text
        y 小  ↑ 远（靠近屏幕上方）
              │     玩家站在敌人上方 → 应该被敌人挡住
              │
        y 大  ↓ 近（靠近屏幕下方）
                   玩家站在敌人下方 → 应该挡住敌人
```

关键细节：用**脚底 y**，不是矩形中心的 y。角色精灵的脚落在碰撞盒底边，遮挡关系也是由脚决定的。用中心 y 会在两个身高不同的角色交错时排反——这个坑在 §5.1 展开。

## 二、为什么在游戏里重要

### 2.1 408 · 数据结构：把 O(n²) 降成 O(n log n)

如果不排序，要正确画出 n 个互相遮挡的物体，理论上得对每一对判断"谁该盖住谁"——O(n²) 次比较，然后还得想办法把结果变成一个绘制序列（本质是拓扑排序）。

排序直接把它塌成：

```text
一次 O(n log n) 的排序  +  一次 O(n) 的线性绘制
```

100 个实体：O(n²) = 10000 次比较，O(n log n) ≈ 700 次。**差 14 倍**，而且实体数一多差距更夸张。这就是"排好序再画"在工业界成为默认做法的全部原因——不是因为它优雅，是因为它便宜。

### 2.2 408 · 算法：比较排序、复杂度、稳定性

`std::sort` 是**比较排序**（comparison sort）：它不看数值本身，只调用你的比较器问"a 该排在 b 前面吗"。所以它能排序任何类型——只要比较器合法。

| 算法 | 平均复杂度 | 最坏 | 稳定 | 什么时候用 |
| --- | --- | --- | --- | --- |
| `std::sort` | O(n log n) | O(n log n)（C++11 起） | ❌ | 默认选择，键唯一时足够 |
| `std::stable_sort` | O(n log n) | O(n log n) | ✅ | 键可能相等，且"相等时保持原顺序"有语义 |
| `std::partial_sort` | O(n log k) | — | ❌ | 只取前 k 名（如排行榜 Top 10） |
| 冒泡/插入 | O(n²) | O(n²) | ✅ | n < 20 时反而更快（常数小），教学用 |

**稳定性**的意思是：比较器认为"相等"的两个元素，排完后保持原来的相对顺序。为什么重要？假设两个敌人脚底 y 完全相同，你希望先加入的那个先画（后加入的盖住它）——如果不稳定，每帧顺序可能随机抖动，画面会闪烁。

### 2.3 一个更省的办法：把"稳定"编进 key

既然"y 相同则按加入顺序"，那就给每个对象一个递增序号 `seq`，把它作为**最后一个比较字段**：

```cpp
if (a.layer != b.layer) return a.layer < b.layer;
if (a.footY  != b.footY) return a.footY  < b.footY;
return a.seq < b.seq;   // 永远不相等 → 结果确定
```

这样比较器对所有元素都给出确定的答案，`std::sort`（不稳定）也不会抖动。**用数据解决稳定性问题，比换算法更可控**——这也是 18 号"schema 表达差异"思想的延续。

### 2.4 408 · 组成原理：别移动大对象，排序指针

`std::sort` 会频繁交换元素。如果 vector 里装的是 `EntityPlayer`、`EntityEnemy` 本身，一次交换就要搬走纹理句柄、插值状态、几十字节的成员——更糟的是，移动可能让 RAII 资源反复构造/析构（见 §五）。

正确做法：**排一张轻量的索引表**。

```text
worldObjects: [unique_ptr<GameObject>]   ← 实体本体，永不动
renderList:   [RenderItem{GameObject*, key}]  ← 每帧重建的 16 字节小结构，随便交换
```

两个收益：

1. 交换 16 字节而不是整个实体；
2. 排序后**顺序访问**指针数组，而实体本体在堆上四处分散——顺序访问的是那张紧凑表，缓存友好。

> 这就是 OS 里"页表"思想的缩小版：不改物理页的位置，只改映射关系。排序改的是"绘制顺序"这张映射，不是对象本身。

## 三、怎么做

### 3.1 两层问题，分两次解决

```text
硬层：RenderLayer 枚举（Floor/Decal/Item/Actor/Overhead/UI）
       → 编译期常量，永不排序

软层：Actor 内部按 footY 排序
       → 运行期数据，每帧可能变
```

把它们合成一个 `RenderOrder` 结构，用三字段比较器一次排完——**枚举在前，所以硬层永远压得住软层**。

### 3.2 排序键的定义

```cpp
/**
 * @brief 渲染顺序键：字典序比较（层 → 脚底 y → 加入序号）。
 */
struct RenderOrder {
    RenderLayer layer = RenderLayer::Actor;  ///< 硬层
    float       footY = 0.f;                 ///< 软层：脚底在世界坐标中的 y
    int         seq   = 0;                   ///< 同一 y 时的稳定化序号
};
```

`footY` 怎么取？对玩家是 `collisionRect_.y + collisionRect_.h`（脚底），对敌人同理。**不要拿精灵中心点**。

### 3.3 严格弱序（Strict Weak Ordering）—— 最容易踩的 C++ 坑

`std::sort` 要求比较器满足严格弱序，其中最关键的一条是：

> **`comp(a, a)` 必须为 `false`。**

所以比较器只能用 `<`，**绝不能用 `<=`**：

```cpp
// ❌ 未定义行为：相等时 comp(a,a)==true，排序可能出现任何结果（包括崩溃）
return a.footY <= b.footY;

// ✅ 严格弱序
return a.footY < b.footY;
```

为什么 `<=` 会出事？`std::sort` 内部用"a < b 且 b < a 则相等"来判断等价类。`<=` 让每个元素都不等价于自己，等价类逻辑全线崩溃，introsort 的分区不变量被破坏——结果不是"排得不太对"，而是**未定义行为**。这类 bug 在 debug 下可能看不出来，release 优化后突然乱序。

> 408 映射：这就是"算法的前提条件"和"算法的实现"分离——复杂度分析再漂亮，前提不满足时结论一律不成立。

### 3.4 代码：把排序键挂到 GameObject 接口上

```cpp
// src/gameobject/GameObject.hpp
enum class RenderLayer : int {
    Floor = 0, Decal = 1, Item = 2,
    Actor = 3, Overhead = 4, UI = 5,
};

struct RenderOrder {
    RenderLayer layer = RenderLayer::Actor;
    float       footY = 0.f;
    int         seq   = 0;
};

/// 严格弱序：层 → 脚底 y → 序号，三项都只用到 `<`
inline bool operator<(const RenderOrder& a, const RenderOrder& b) {
    if (a.layer != b.layer) return static_cast<int>(a.layer) < static_cast<int>(b.layer);
    if (a.footY != b.footY) return a.footY < b.footY;
    return a.seq < b.seq;
}
```

`GameObject` 加一个纯虚函数，让每个实体自己报告该排在哪：

```cpp
virtual RenderOrder GetRenderOrder() const = 0;
```

玩家的返回值（用脚底 y）：

```cpp
RenderOrder GetRenderOrder() const override {
    const SDL_FRect r = collisionRect_.Rendered(lastAlpha_);   // 与绘制同一拍的位置
    return {RenderLayer::Actor, r.y + r.h, seq_};
}
```

> **插值一致性**：排序用的 y 必须和 `Draw()` 用的 y 来自同一拍。否则画面上玩家已经走过去了，排序还按上一拍的位置——会出现"刚好交错时闪一下"的幽灵 bug。`interpolation` 要一起传进 `GetRenderOrder()`，或在 `Draw()` 前统一快照一次（后者更稳）。

### 3.5 绘制循环

```cpp
// 成员：std::vector<RenderItem> renderList_;（复用，不清空容量）

renderList_.clear();
renderList_.reserve(worldObjects.size());
int seq = 0;
for (const auto& obj : worldObjects) {
    renderList_.push_back({obj.get(), obj->GetRenderOrder(interpolation, seq)});
}
std::sort(renderList_.begin(), renderList_.end(),
          [](const RenderItem& a, const RenderItem& b) { return a.order < b.order; });

for (const RenderItem& item : renderList_) {
    item.object->Draw(renderer_.Get(), interpolation);
}
```

`reserve()` 是**每帧重复调用也没关系**的：容量够时它什么都不做。把它放在循环开始前，避免头几帧反复扩容（12 号讲过的均摊复杂度）。

### 3.6 什么时候排序：先做对的，再谈快

| 策略 | 代价 | 适用 |
| --- | --- | --- |
| 每帧排序 | O(n log n) / 帧 | n < 几百，最简单可靠 ← **现在用这个** |
| 脏标记 | 只在实体增删/移动时排 | 实体多且大部分静止 |
| 桶排序 / y 排序表 | O(n + 范围) | 网格游戏：y 只有几十种，直接分桶 |

**不要一开始上脏标记。** 你现在 n=2，每帧排 2 个元素几乎是零成本；引入缓存失效逻辑反而多一个"忘了标脏 → 顺序不更新"的 bug 源。等真的 profiling 看到排序占比再说——和 10 号"不要过早优化"同一条纪律。

### 3.7 地牢里的完整图层表（提前给 D 阶段用）

| 层 | 内容 | 排序方式 |
| --- | --- | --- |
| `Floor` | 瓦片地面、房间底色 | 不排（网格顺序即可） |
| `Decal` | 血迹、脚印、地面提示圈 | 不排 |
| `Item` | 掉落物、地上的火把 | 按 footY |
| `Actor` | 玩家、敌人、NPC | 按 footY |
| `Overhead` | 墙顶、树冠、门楣 | 按 footY（在头顶之上） |
| `UI` | 血条、消息日志、背包 | 不排（永远最后） |

> 注意 `Overhead` 也是按 footY 排的——一棵树站在玩家下方时，树冠应该挡住玩家；站在玩家上方时，玩家应该从树前面走过。**"墙/树挡人不挡"不是层属性，是位置关系。**

## 五、常见坑

### 5.1 用中心 y 当深度

两个角色身高不同：高个子精灵中心 y 比矮个子高，但脚站在同一行。用中心 y 会让他们前后关系排反。

**正解**：统一用脚底 `y + h`，这也和 3/4 视角的遮挡直觉一致。

### 5.2 比较器写 `<=`

见 §3.3。这是未定义行为，不是"稍微排错"。**任何比较器写完先问自己：`comp(a, a)` 是不是 `false`？**

### 5.3 把 UI 塞进同一个排序数组

UI 不该按 y 排——它永远最后画。塞进同一个数组就得靠"给 UI 一个巨大 y"这种 hack，加第二个 UI 元素时立刻崩。

**正解**：用 `RenderLayer` 枚举做第一关键字。

### 5.4 排序时移动实体本体

`std::sort` 交换的是完整对象：纹理句柄、插值状态全被搬来搬去，RAII 对象反复移动构造。

**正解**：排轻量索引表（§2.4）。

### 5.5 排序键和绘制位置不是同一拍

用 `collisionRect_.Current()` 排序、用 `Rendered(alpha)` 绘制，在两拍之间交错时会闪一帧。

**正解**：排序键和 `Draw()` 用同一个插值系数（最好在 `Draw()` 之前统一取一次快照）。

### 5.6 过早引入脏标记

n=2 时每帧排序的成本低于维护"脏"状态的分支预测开销。

**正解**：先写无脑每帧排序，profiling 有证据再优化。
