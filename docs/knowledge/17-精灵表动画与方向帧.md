# 17 · 精灵表动画与方向帧：让静止的格子动起来

> 前置：16 号《精灵图与瓦片图集》——`srcRect` 决定"取哪一格"。
> 本文回答两个问题：**格子什么时候换？** 以及 **"方向 + 状态"怎么落到具体的行列上？**

---

## 一、这是什么

### 1.1 16 号只解决了"取一格"，没有解决"换格"

16 号做到了：给定一个帧索引，算出 `srcRect`，把那一格画出来。

但这样的角色是**冻住的**——不管你按不按 W 键，显示的都是同一格。真正的动画需要第三样东西：

```text
帧索引（取哪一格）  ← 16 号已有
时间（什么时候换）  ← 本文补上
状态（该用哪一行）  ← 本文补上
```

三者合起来，才叫"动画"。

### 1.2 本项目实际的表长什么样

`tools/gen_player_sheet.ps1` 生成的是 **128×128**：

```text
每帧 32×32，4 列 × 4 行 = 16 格

        列0      列1      列2      列3      ← 帧序（时间轴）
行0  ┌────────┬────────┬────────┬────────┐
  下 │  walk0 │  walk1 │  walk2 │  walk3 │
行1  ├────────┼────────┼────────┼────────┤
  左 │  walk0 │  walk1 │  walk2 │  walk3 │
行2  ├────────┼────────┼────────┼────────┤
  右 │  walk0 │  walk1 │  walk2 │  walk3 │
行3  ├────────┼────────┼────────┼────────┤
  上 │  walk0 │  walk1 │  walk2 │  walk3 │
     └────────┴────────┴────────┴────────┘
```

这张表的两个维度含义完全不同：

| 维度 | 含义 | 谁决定 |
| --- | --- | --- |
| **行**（row） | 方向 / 动画片段 | 玩家的**朝向**和**状态** |
| **列**（col） | 该片段内的第几帧 | **时间** |

所以帧索引不是一维的 `0..15`，而是**两个独立的量**拼出来的：

```text
srcX = col * 32        ← 时间推进
srcY = row * 32        ← 方向 / 状态决定
```

> 这一点很容易搞混。如果把 16 格当成一个 16 帧的循环播放，人物就会"走着走着突然转身"——因为第 3 帧之后自然跳到了下一行。

### 1.3 三个术语，先钉死

| 术语 | 英文 | 含义 |
| --- | --- | --- |
| 动画片段 | clip | 一段完整动画：哪一行、几帧、每帧多久、是否循环 |
| 帧索引 | `frameIndex` | 当前片段内的第几帧（`0..frameCount-1`） |
| 帧时长 | `frameTime` | 每帧停留多久（秒） |
| 播放模式 | loop / once | 循环播放（走路）还是播完停住（攻击） |

### 1.4 帧时长决定"手感"

参考素材实测结果（`Test/Analysis` 里那三个 GIF）：

```text
CasualWalk : 8 帧 × 100ms = 800ms 一圈
ZeroRun    : 10 帧 × 100ms = 1000ms
ZeroRoll   : 7 帧 × 100ms = 700ms
```

**10fps（100ms/帧）是像素动画的行业默认**。它远低于 60fps 渲染帧率，但看起来并不卡——因为人眼判断"动"靠的是**位移的变化**，不是帧数。

> 手感的调整基本就在这一个数字上：100ms 偏"从容"，60~80ms 偏"急促"，150ms 以上像"慢动作"。

## 二、为什么在游戏里重要

### 2.1 408 · 计算机组成原理：这就是"时钟分频"

逻辑帧率固定 60Hz（11 号），动画要 10Hz。怎么从 60 变 10？

```text
60Hz 时钟 ──► 计数器 ──► 每数到 6 输出一个脉冲 ──► 10Hz 动画帧
```

这正是 CPU 里**分频器**（clock divider）的做法：主频经过计数器分频，得到低速时钟驱动外设。

```text
accumulator += dt          // 每个逻辑步累加 16.67ms
accumulator >= 100ms ?     // 攒够一个完整动画周期了吗
    → 触发一次换帧，并扣掉 100ms
```

`accumulator_` 本质就是一个**分频计数器**，只不过它数的是浮点时间而不是整数脉冲。

### 2.2 408 · 操作系统：这就是"时间片轮转"

每个动画帧固定占用 100ms，和 OS 给进程分配的**时间片**（time slice）是同一个模型：

```text
时间片 100ms 用完 → 切换到"下一个"（下一帧）→ 剩余量继续累计
```

区别只在 OS 的"下一个"是别的进程，我们的是下一帧图像。

### 2.3 408 · 数据结构：二维索引 ↔ 行优先一维化

图集内存里是**连续**的一片（行优先），但逻辑上要按 `(row, col)` 访问：

```text
一维位置 = row * cols + col          // 正向：二维 → 一维
row      = i / cols                  // 反向：商
col      = i % cols                  // 反向：余数
```

和 16 号、以及以后 `map[y][x]` 的 `y * width + x` 是**同一个公式**。

本文的做法是**不把它一维化**——直接分开保存 `row`（方向）和 `frameIndex`（列）。因为这两者的**变化频率完全不同**：方向按键才变，帧每 100ms 都变。混成一个一维索引，每次换方向都要重算、还容易越界。

> 结论：先问"这两个维度谁在变"，再决定合并还是分离。

### 2.4 408 · 数据结构：有限状态机（FSM）

角色的动画是个状态机：

```text
       按下方向键
  Idle ──────────► Walk
    ▲               │
    └───────────────┘
        松开所有方向键

  Walk ──攻击键──► Attack ──播完──► Idle
```

状态机的三条硬规矩：

1. **每个状态有自己的片段**（帧数、时长、是否循环都不同）
2. **帧索引不能跨状态复用**——攻击有 6 帧，走路只有 4 帧，拿走路的 `frameIndex=5` 去攻击片段里查就越界
3. **进入状态要初始化**（`frameIndex=0`、`accumulator=0`、`playing=true`）

### 2.5 为什么动画绝不能绑在渲染帧上

假如你写：

```cpp
void Render() {
    ++frameIndex;   // 每渲染一帧就换一帧图
    Draw();
}
```

在 60Hz 显示器上动画是 60fps；换到 144Hz 显示器，动画**快 2.4 倍**；玩家开垂直同步又变回 60。同一份代码，三种速度。

**正确做法**：动画推进放在固定步长的 `Update(dt)` 里，用 `dt` 换算（11 号）。这样逻辑与显示器无关，速度恒定、结果可复现（determinism）。

## 三、怎么做

### 3.1 数据结构：把"片段"做成表

```cpp
/** @brief 一段动画的静态描述（不随时间变化）。 */
struct AnimationClip {
    int   row;         ///< 在精灵表中的行号（0=下 1=左 2=右 3=上）
    int   frameCount;  ///< 本片段共几帧
    float frameTime;   ///< 每帧停留时长（秒）
    bool  loop;        ///< true=循环（走路），false=播完停住（攻击）
};
```

片段表（数据驱动，不写死在函数里）：

```cpp
// 本项目当前的 128×128 表：每个方向 4 帧，10fps
constexpr AnimationClip kWalkDown { 0, 4, 0.10f, true };
constexpr AnimationClip kWalkLeft { 1, 4, 0.10f, true };
constexpr AnimationClip kWalkRight{ 2, 4, 0.10f, true };
constexpr AnimationClip kWalkUp   { 3, 4, 0.10f, true };
```

> 为什么用表而不是 `switch` 里现场算？因为 C 阶段接入 `manifest.json` 后，**这张表会变成数据文件**，代码一行不用改。

### 3.2 运行时状态：随时间变化的部分

```cpp
class SpriteAnimator {
public:
    void Play(const AnimationClip& clip) {
        clip_        = &clip;
        frameIndex_  = 0;
        accumulator_ = 0.0f;
        playing_     = true;
    }

    /** @brief 推进动画。dt 必须是逻辑步长（秒）。 */
    void Update(float dt) {
        if (!playing_ || clip_ == nullptr || clip_->frameTime <= 0.0f) return;

        accumulator_ += dt;
        while (accumulator_ >= clip_->frameTime) {
            accumulator_ -= clip_->frameTime;   // 扣掉一整帧，保留余数
            if (++frameIndex_ >= clip_->frameCount) {
                if (clip_->loop) {
                    frameIndex_ = 0;
                } else {
                    frameIndex_ = clip_->frameCount - 1;
                    playing_    = false;
                }
            }
        }
    }

    int Row()        const { return clip_ ? clip_->row : 0; }
    int FrameIndex() const { return frameIndex_; }

private:
    const AnimationClip* clip_ = nullptr;
    int   frameIndex_  = 0;
    float accumulator_ = 0.0f;
    bool  playing_     = false;
};
```

三个细节，每一个都有实际后果：

| 写法 | 为什么不能那样写 |
| --- | --- |
| 用 `while` 而不是 `if` | 卡顿一次（`dt=0.35s`）要一次补 3 帧；用 `if` 只会补 1 帧，动画变慢且越拖越慢 |
| `accumulator_ -= frameTime` 而不是 `= 0` | 归零会丢掉不足一帧的余数（最大 99ms），长期运行动画会**持续变慢**（丢帧累积） |
| `frameCount` 取**本片段**的，不是全表帧数 | 全表 16 格是"4 行 × 4 列"，但攻击片段可能是 6 帧，混用必越界 |

### 3.3 算出 srcRect（接 16 号）

```cpp
constexpr int FRAME_W = 32;
constexpr int FRAME_H = 32;

/** @brief 由 (行, 列) 求图集源矩形。 */
SDL_FRect SrcRect(int row, int frameIndex) {
    return SDL_FRect{
        static_cast<float>(frameIndex * FRAME_W),
        static_cast<float>(row * FRAME_H),
        static_cast<float>(FRAME_W),
        static_cast<float>(FRAME_H)
    };
}
```

注意公式里**没有取模**：`frameIndex` 永远在 `0..frameCount-1` 范围内，由 `Update` 保证；`row` 由方向保证。**边界约束是上游的职责**，下游算坐标时不做二次修补——这样出了 bug 能一眼看出是谁没守规矩。

### 3.4 方向 → 行号：让编译器帮你对号入座

```cpp
/** @brief 朝向。取值必须与精灵表的行序一致。 */
enum class Direction : int {
    Down  = 0,
    Left  = 1,
    Right = 2,
    Up    = 3,
};
```

好处：

```cpp
const AnimationClip& WalkClipOf(Direction dir) {
    switch (dir) {                       // 枚举用 switch，新增方向时编译器会警告漏分支
        case Direction::Down:  return kWalkDown;
        case Direction::Left:  return kWalkLeft;
        case Direction::Right: return kWalkRight;
        case Direction::Up:    return kWalkUp;
    }
    return kWalkDown;                    // 兜底（正常不会走到）
}
```

> **行序不是想当然的**：`gen_player_sheet.ps1` 里写的是 `DOWN=0, LEFT=1, RIGHT=2, UP=3`。如果你在 C++ 里按"上右下左"写，画面就会出现"按上键人物向左走"这种诡异 bug。**以资源生成脚本为准，并把行序抄进注释。**

### 3.5 与位置插值的关系：两套时钟，不要混

11 号引入的插值负责"位置平滑"，本文的 accumulator 负责"换帧"。它们是**两个独立的时间消费者**：

| | 位置 | 动画帧 |
| --- | --- | --- |
| 连续性 | **连续**（像素级小数） | **离散**（整数帧） |
| 插值 | ✅ 要 | ❌ **绝不能** |
| 驱动方式 | `prev`/`curr` 按 `alpha` 混合 | 累加器攒够一个 `frameTime` 才跳 |
| 抖动后果 | 移动卡顿 | 出现"半帧"（两张脸叠在一起） |

所以：

```cpp
// Update：逻辑时基
animator_.Update(FIXED_DT);        // 动画按逻辑步长推进

// Render：渲染时基
alpha = accumulator / FIXED_DT;    // 只给位置用
Draw(lerp(prev, curr, alpha), animator_.Row(), animator_.FrameIndex());
```

### 3.6 回合制网格下的特殊之处（本项目）

Roguelike 是**离散步进**：按一次方向键，角色从 (x,y) 走到 (x+1,y)，中间用 200~300ms 补间。

这意味着动画和普通 ARPG 不一样：

```text
普通 ARPG：按住方向键 → 一直播走路动画
本项目    ：按一次 → 走一格（300ms）→ 停下 → 定格
```

两种处理都合理，看想要的手感：

| 方案 | 做法 | 效果 |
| --- | --- | --- |
| A · 整圈播放 | 一格补间 = 一个完整的 4 帧循环 | 每一步"踏一下"，节奏清晰 |
| B · 循环到站 | 补间期间循环播放，到达时复位到第 0 帧 | 步频快时更连贯 |
| C · 时间缩放 | 把 `frameTime` = 补间时长 / 帧数 | 格子走得快，动画也快 |

> 建议先做 **A**：一格一圈最好调，也最容易看出"帧序有没有错"。

### 3.7 常见坑

| 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- |
| 用 `if` 推进 | 卡顿后动画永久变慢 | 必须 `while` 补帧 |
| 累加器归零 | 长时间运行后动画变慢 | `-=` 而不是 `= 0` |
| 帧数用全表 16 | 攻击/待机时越界或串行 | 用**本片段**的 `frameCount` |
| 行序与素材不符 | 按键与动作方向不一致 | 抄生成脚本的定义，写进注释 |
| 动画绑渲染帧 | 换显示器速度就变 | 用 `dt` 驱动，放在 `Update` |
| 停下不处理 | 定格在"抬腿"的怪姿势 | 切回 Idle 时 `frameIndex = 0` |
| 切状态不复位 | 攻击播到一半又从头抖一下 | `Play()` 里统一复位三个量 |
| 方向键抖动 | 每帧重播 `Play()`，动画卡在第 0 帧 | 只在**方向真的改变**时调用 `Play()` |
| `frameTime = 0` | 死循环或除零 | `Update` 开头早退 |
| 一次性动画重复触发 | 攻击动画疯狂重播 | 用 `playing_` 标志 + 状态机守卫 |

## 四、和已知知识的挂钩

| 已有知识 | 本文的延伸 |

| 16 号：图集取帧 | 本文补上"什么时候换帧"和"用哪一行" |
