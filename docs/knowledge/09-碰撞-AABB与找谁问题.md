# 09 · 碰撞：当两个矩形相遇——AABB 与"找谁"问题的序曲（408·数据结构续篇）

> 背景与上下文：上一课的 clamp 贴墙，其实就是"矩形 vs 窗口边缘"的单向碰撞。
> 本课给它换个对手：**两个矩形相遇**。你会看到判定本身只需要四个不等式，
> 而这门学科真正的大课题不是"怎么判"，而是**"对象多起来后和谁判"**——
> 408 的散列（哈希）思想将以前瞻姿态登场。

---

## 一、一句话核心

> **碰撞检测 = 几何判定（谁重叠了）＋ 碰撞响应（重叠了怎么办，规则你说了算）。**
> 轴对齐矩形（AABB）的相交判定只需四个不等式；
> 而对象一多，真正的难题从"怎么判"变成"和谁判"——那是空间管理的主场。

## 二、AABB 相交判定的数学（四个不等式的由来）

AABB = **Axis-Aligned Bounding Box**（轴对齐包围盒）："对齐"意思是边都平行于
x/y 轴，不旋转——2D 游戏九成见到的碰撞就是它，简单、快、够用。

判定灵感和"两个数区间是否重叠"同源。先看一维（x 轴）：

```text
x 轴视角：
        a.x          a.x+a.w
         ├====[ a ]====┤
                   ├====[ b ]====┤
                   b.x         b.x+b.w
     ↑ 若 a 的右边缘超过 b 的左边缘 → x 轴上"有重叠"
```

两条**彼此不打照面**的情形：a 整体在 b 左边（a.x+a.w <= b.x），或 a 整体在 b 右边
（b.x+b.w <= a.x）。用"至少一边分开 = 不相交"取反（De Morgan 律）：

```text
x 轴有重叠 ⇔  a.x < b.x + b.w   并且   b.x + b.w > a.x   （等价写法：a.x+a.w > b.x）
```

y 轴完全同构，再来两个。**四个不等式 = 两个轴各证明"有重叠"**——这就是全部数学：

```cpp
if (a.x < b.x + b.w && a.x + a.w > b.x &&
    a.y < b.y + b.h && a.y + a.h > b.y) {
    // 相交！
}
```

**为什么用 `<` 不用 `<=`**：正好贴边（a 的右边 == b 的左边）时，`<=` 会把"贴着"
也算成碰撞。游戏里通常"贴着不算"（像贴墙滑行），而且浮点世界里为了**同一个
边缘值**反复比较，把"贴边"排除在外是最稳的设计决策——这是品味，不是迷信。

## 三、实用主义心境：先蛮力，够用就行

两个矩形 = 一次判定。100 个矩形 = 两两判定：双重循环，约 n×n = 一万次——
你上一课已算过键盘快照一次 O(1)，这一万次也只是每帧的常数级常数。
**60 fps 下每秒 60 万次整数比较，对现代 CPU 是毛毛雨**（408·算法分析：
先算数量级，再谈优化）。

所以本课蓝图就是**最直接的成对判定**。空间管理的高级手段**下不为例地先欠着**——

## 四、前瞻：对象一多，真正的问题变成"找谁"（408·散列登场预告）

想象将来 500 个对象：两两判定 = 约 12.5 万次/帧。这时工程界的老智慧出场——
**空间哈希（Spatial Hash）**：

```text
把世界切成固定尺寸的格子（如 128×128 像素/格）：
+------+------+------+
|  A   |      |  B   |
+------+------+------+
|      | A,B  |      |   ← A 和 B 在同一格：只对同格对象做判定
+------+------+------+

408 翻译：这就是散列表（数组 + 哈希函数）！
  key   = "格子坐标"（把 x,y 换算进格号）
  value = 登记在这格里的对象列表（链表/动态数组）
效果：只挑战"住得近"的候选者，远处的对象连名号都不配见到。
```

值得记住的判断标准：**蛮力先上，O(n²) 真的疼了再换空间结构**——
过早优化的大忌在数据结构课里同样成立。（本课不实现，空间哈希的代码留给"实体规模化"之后的那课。）

## 五、本课实战蓝图

**新文件 `src/core/Collision.hpp`（header-only：函数小而稳定，不需要 .cpp）**：

```cpp
// Collision.hpp —— 碰撞判定工具（header-only：inline 函数定义在头文件里，ODR 特例）
#pragma once
#include <SDL3/SDL_rect.h>    // SDL_FRect 的家（比整个 SDL.h 更 meet 最小化）

// AABB 相交判定：两个轴对齐矩形是否重叠
inline bool Intersects(const SDL_FRect& a, const SDL_FRect& b) {
    return a.x < b.x + b.w
        && a.x + a.w > b.x
        && a.y < b.y + b.h
        && a.y + a.h > b.y;
}
```

说明：`inline` 写在头文件里是 03 课 ODR 特例的正式上岗（每个翻译单元各有一份
一模一样的定义，链接器合体）；这是 **header-only 工具**的标配形态，CMake 一行都不用动。

**`Application::Run()` 升级（拼图式改动，别推倒重写）**：

```cpp
// ① 矩形升级为有名字的两位选手（顺便把上一课的 rect 改名 hero）
SDL_FRect hero  {640.0f, 380.0f, 160.0f, 120.0f};   // 主角（方向键控制，已有）
SDL_FRect enemy {200.0f, 200.0f, 120.0f, 120.0f};   // 敌人（静止，被抓到就重生）

// ② while 循环开头，加一行：一局一个随机种子（每次运行不同布局）
std::srand(static_cast<unsigned>(std::time(nullptr)));

// ③ update 段的 clamp 之后，加判定 + 最小响应：
if (Intersects(hero, enemy)) {
    std::cout << "hit! at (" << hero.x << ", " << hero.y << ")\n";
    // 响应规则一页纸：敌人瞬移到随机位置（x 限制在 0 ~ 窗宽−敌宽，保证不出界）
    enemy.x = static_cast<float>(std::rand() % (winW - static_cast<int>(enemy.w)));
    enemy.y = static_cast<float>(std::rand() % (winH - static_cast<int>(enemy.h)));
}

// ④ render 段画两个人（敌人换绿色）：
SDL_SetRenderDrawColor(renderer_.Get(), 32, 32, 48, SDL_ALPHA_OPAQUE);
SDL_RenderClear(renderer_.Get());
SDL_SetRenderDrawColor(renderer_.Get(), 230, 120, 70, SDL_ALPHA_OPAQUE);
SDL_RenderFillRect(renderer_.Get(), &hero);
SDL_SetRenderDrawColor(renderer_.Get(), 130, 220, 130, SDL_ALPHA_OPAQUE);
SDL_RenderFillRect(renderer_.Get(), &enemy);
SDL_RenderPresent(renderer_.Get());
```

include 增补（.cpp 顶部，全部配齐）：

```cpp
#include <cstdlib>    // std::rand（伪随机数）
#include <ctime>      // std::time（拿当前时间当随机种子）
```

**伪随机不是真随机**：`srand` 把"当前时间"作为序列起点，`rand` 沿着序列吐数——
同一 seed 序列一模一样。它的另一面很金贵：**固定 seed = 场景可复现 = 调试利器**
（业界叫"确定性"，408·OS 随机数章节的同族知识）。将来换 `<random>` 是为了distribution 质量，不是审美。

## 六、常见坑

1. **取余分布不均**——rand 的取余 `std::rand() % n`：余数分布略偏（`RAND_MAX` 不是 n 的整数倍），
   重生场景不敏感，知道有此一档即可；
2. **敌人重生出窗**——重生公式里的 `winW - enemy.w` 就是让边界 clamp 思想
   **预置进生成**（生成时就不越界，比画出来再拽回来更朴素）；
3. **判定写在 render 后面**——响应将晚一帧才影响画面；判定永远紧跟 update；
4. **四行不等式手滑**——把 `<` 与 `>` 方向写反是最常见 bug：症状是"分也当成碰、碰也不响应"。
   症状与判定贴边设计（第二节）不一致时，先逐行圈四个比较符。

## 七、概念词典

| 术语 | 一句话解释 |
| --- | --- |
| AABB | 轴对齐包围盒：边平行于坐标轴的矩形，2D 碰撞的基本单元 |
| 相交判定 | "谁与谁重叠"的几何计算，本课=四个不等式 |
| 碰撞响应 | 重叠后的规则，从瞬移到物理反弹都算（复杂度由需求决定） |
| O(n²) 蛮力 | 两两全查；数量级不大时的正解 |
| 空间哈希 | 切格子登记位置，只判定同格候选——散列表思想的空间版 |
| header-only | 整个工具就是一个头文件（背后是 inline 的 ODR 特例），无需 .cpp |
| 伪随机 / seed | 序列起点相同则序列相同；固定 = 可复现 = 可调试 |
| De Morgan 律 | "至少一边分开 = 不相交"取反成"两边都有重叠 = 相交" |

## 八、记忆锚点 🎯

> AABB 四个不等式 = 两轴各证"有重叠"；贴边不算碰，浮点更求稳。
> 数量小就蛮力 O(n²)，真疼了才上空间哈希——
> **判定归几何，响应归规则，模拟归远方**。分离三件套，引擎的神秘面就此揭开一瞬间。

## 九、自测问题（回收后进帧率课）

1. n=3 时双重循环判定多少次？n=100 时呢？再算算：**如果只判定"同格"候选**
   （500 个对象分布均匀、每格平均 3 个），又是多少次？——体会空间哈希砍的不是计算，
   是**没必要的配对**。
2. 判定用 `<` 时，两个矩形"正好贴边"（主角的右边缘 == 敌人的左边缘）报什么？
   如果游戏想要"贴边也扣血"，该改哪个字符？这属于判定还是响应？
3. 空间哈希里，你愿意让它把 key 取成"对象的 ID"吗？为什么格子坐标才是 key
   而 ID 只能是 value 里的内容？（提示：我们要问的是"这一小片地面上有什么"）
