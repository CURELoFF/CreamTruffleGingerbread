# 11 · 游戏循环成人式：累加器分账、固定步长与插值

> 背景与上下文：10 号课补录里你亲口推理出了"两个账本"——update 和 render
> 每秒次数可以不同。本课正式实施这个结构：**逻辑步进锁 60Hz 不漂移，
> 渲染跟着显示器走，两拍之间的时刻用插值补帧**；
> 顺带把 09/10 课预告了两回的"隧穿"债一次还清（固定步长就是还债的主角）。

---

## 一、一句话核心

> **update 攒账、按固定拍子还账（一帧可能还 0~N 拍）；render 跟显示器节奏走。**
> 渲染时刻落在两次逻辑步进"之间"时，用 `prev + (curr − prev) × α` 在两个状态间
> 脑补出中间帧——从此 update 的次数由账本决定，不再被任何显示器摆布。

## 二、为什么值得成人式？三个动机（其中一个是欠了两课的债）

**动机 ①：隧穿被"结构性排除"（还债）**

可变 dt 世界里，一帧的状态改变量 = 速度 × dt，而 dt 只被钳制在上限——
将来出现高速物体（子弹 2000 px/s × 0.1s 钳制 = 一帧 200 像素）时，
一帧就能整个跨过 50 像素宽的敌人，碰撞判定"没看见它"。这就是隧穿。

固定步长下：

```text
每次 update 的状态改变量 = 速度 × STEP = 64 × 1/60 ≈ 1.07 像素（恒定，有上限）
判定紧跟每一步 → 物体每走 1.07 像素就被检查一次
→ 跨过任何（比 1.07 像素宽的）东西在结构上不可能发生，与帧率、卡顿无关。
```

**动机 ②：确定性（determinism）——调试金矿**

可变 dt 的隐藏代价：60Hz 机器和 144Hz 机器上跑同样的输入，每帧的
位置数字全不一样——状态轨迹分岔了。固定步长下，update 的次数与内容
只由"账本"决定，与渲染快慢、屏幕刷新率无关：

```text
固定步长 + 固定随机种子 = 同样输入 → 完全相同的游戏轨迹可复现
→ 测出的 bug 永远能重现（编程工业里最值钱的性质之一）
```

**动机 ③：两账分家，为多线程铺路**

update 不再住在"被 Present 卡节奏"的循环里。将来逻辑/渲染进两个线程
（UE 的 GameThread / RenderThread 家谱），就是把这个单线程结构放大。

## 三、累加器（accumulator）：时间就是余额

```text
真实时间每帧流逝 → acc += frameTime    （往账本里存"欠 update 的秒数"）
固定拍子 STEP = 1/60 秒：
   只要 acc ≥ STEP → update(STEP)，acc −= STEP   （还一拍，可能一帧还 0~N 拍）
渲染 → 每 vsync 一帧；两拍之间时刻的插值系数 α = acc / STEP（欠账余量比例）
```

三台机器上的行为账（设逻辑 60Hz）：

```text
60Hz 显示器： 每帧攒 ~16.7ms → 正好每帧还 1 拍（update 60：render 60 = 1:1）
144Hz 显示器：每帧攒 ~6.9ms → 每 ~2.4 帧才够一拍（update 60 : render 144）
             逻辑拍子出现"3:2:3:2"的复节奏——插值在渲染层把它抹平
掉帧/断点 0.2 秒 → 一次还 12 拍（catch-up 补拍）：状态瞬间追上，不丢不欠
```

**警钟：死亡螺旋（spiral of death）**——如果 update 本身慢于 STEP，
还账速度赶不上进账速度，acc 永不清空、越攒越多。上节课的 clamp
（frameTime 上限 0.1s）就是它的牢笼：**最坏情况每帧也只欠 6 拍——螺旋被锁死在笼里**。

## 四、插值（interpolation）：两拍之间的"脑补"

10 课补录的 GameMaker 问答里你已经见过公式，现在把它的三大件配齐：

```text
α = acc / STEP  ∈ [0, 1)     ← "距上一拍已过了百分之几的间隔"
渲染位置 = prev + (curr − prev) × α
```

- `prev`：每拍开拍前存下的快照（`prev = curr` 然后让 update 改 curr）——
  一对象两份状态，这就是**双缓冲（double buffering）思想的雏形**；
- 效果：逻辑 60Hz、渲染 144Hz 时，肉眼看到的不再是"同一帧反复出镜"，而是 144 个各不相同的过渡帧。

**插值的边界：只在"运动"上用，不可用于"事件"**——敌人瞬移重生那一刻，
如果把 prev 到 curr 的位置拿去插值，屏幕会画出一个"幽灵滑行"（敌人从原地
平滑滑到重生点）。规矩：**运动可以插值，事件必须瞬爆——别对事件用运动的手法**。
本课蓝图只对 player 插值，entity 直接画当前值——天然绕开这个坑。
（工程里的正式写法：事件发生时顺带 `prev = curr`，令该帧 α 失效。）

## 五、实战蓝图（改造 Run() 的心脏，别推倒重写）

```cpp
void Application::Run() {
    bool running = true;
    SDL_Event event;

    const Uint64 freq = SDL_GetPerformanceFrequency();
    Uint64 last = SDL_GetPerformanceCounter();
    constexpr double STEP = 1.0 / 60.0;   // 固定步长 60Hz（必须写小数！见坑 1）
    double acc = 0.0;                     // 累加器：欠逻辑账本的时间余额

    SDL_FRect prev  {50.f, 50.f, 100.f, 100.f};   // 插值原料：上一拍快照
    SDL_FRect player{50.f, 50.f, 100.f, 100.f};   // 当前状态（原来的 curr 本体）
    SDL_FRect entity{200.f, 200.f, 50.f, 50.f};

    std::srand(static_cast<unsigned>(std::time(nullptr)));

    while (running) {
        while (SDL_PollEvent(&event)) {
            if (event.type == SDL_EVENT_QUIT) running = false;
        }

        // ① 进账：本帧真实流逝时间（0.1 钳制同时防断点海啸与死亡螺旋）
        const Uint64 now = SDL_GetPerformanceCounter();
        acc += std::min(static_cast<double>(now - last) / static_cast<double>(freq), 0.1);
        last = now;

        // ======= 账本 A：逻辑步进（每拍 1/60 秒，一帧可能还 0~N 拍）=======
        while (acc >= STEP) {
            prev = player;    // 开拍先拍快照（双缓冲雏形）

            const bool* keys = SDL_GetKeyboardState(nullptr);   // 每拍重取（快照本帧有效）
            if (keys[SDL_SCANCODE_ESCAPE]) running = false;

            const float movePerStep = 64.f * static_cast<float>(STEP);  // 每拍恒定 ~1.07px
            if (keys[SDL_SCANCODE_LEFT])  player.x -= movePerStep;
            if (keys[SDL_SCANCODE_RIGHT]) player.x += movePerStep;
            if (keys[SDL_SCANCODE_UP])    player.y -= movePerStep;
            if (keys[SDL_SCANCODE_DOWN])  player.y += movePerStep;

            int winw = 0, winh = 0;
            SDL_GetWindowSize(window_.Get(), &winw, &winh);
            player.x = std::clamp(player.x, 0.f, static_cast<float>(winw) - player.w);
            player.y = std::clamp(player.y, 0.f, static_cast<float>(winh) - player.h);

            // 判定住进固定拍：隧穿从结构上不可能（还债完毕）
            if (Intersects(player, entity)) {
                std::cout << "Hit at " << player.x << "," << player.y << std::endl;
                entity.x = static_cast<float>(std::rand() % (winw - static_cast<int>(entity.w)));
                entity.y = static_cast<float>(std::rand() % (winh - static_cast<int>(entity.h)));
            }

            acc -= STEP;   // 还一拍（坑 4：这行绝不能忘！）
        }

        // ======= 账本 B：渲染（跟 vsync 节拍）=======
        const float alpha = static_cast<float>(acc / STEP);   // ∈ [0,1)
        SDL_FRect display = player;                           // 插值结果就画这个！
        display.x = prev.x + (player.x - prev.x) * alpha;
        display.y = prev.y + (player.y - prev.y) * alpha;

        SDL_SetRenderDrawColor(renderer_.Get(), 32, 32, 48, SDL_ALPHA_OPAQUE);
        SDL_RenderClear(renderer_.Get());
        SDL_SetRenderDrawColor(renderer_.Get(), 230, 120, 70, SDL_ALPHA_OPAQUE);
        SDL_RenderFillRect(renderer_.Get(), &display);        // ← 画 display，不是 player（坑 2）
        SDL_SetRenderDrawColor(renderer_.Get(), 127, 0, 9, SDL_ALPHA_OPAQUE);
        SDL_RenderFillRect(renderer_.Get(), &entity);         // entity 画当前值：瞬移无幻影
        SDL_RenderPresent(renderer_.Get());
    }
    std::cout << "Application clean quit." << std::endl;
}
```

说明（对照你现有代码的迁移点）：

- 原来的 dt/`frameTime` 变量整个退役——时间语义换成"进账/还拍"；
- 移动量不再 `× dt` 而是 `× STEP`——步长固定了，每拍位移是常数；
- `keys`、窗口尺寸、碰撞判定**全搬进内层 while**——它们属于"每拍"而非"每帧"；
- entity 不插值，直接画本体——瞬移幻影天然免疫。

**自由实验（强烈推荐，两个账本亲眼看）**：在循环外加两个计数器
`int updates = 0, renders = 0;`，分别在内层 while 尾和 Present 后 `++`，
再每秒打印一次（可用最朴素的做法：累计 `acc`，满 1.0 时打印后清零）。
你的 60Hz 机器上应看到 60:60；文章第二节解释了 144Hz 机器会看到 60:144。
顺手加 `SDL_Delay(33)` 模拟"渲染很慢的机器"再观察一次（看完拆掉）。

## 六、常见坑

1. **`STEP` 写成 `1 / 60`**——整数除法直接得 0！`while (acc >= 0)` 变成
   永远真 → 死循环，窗口直接冻住。必须 `1.0 / 60.0`（单位纪律：时间永远是浮点，上课就说过）。
2. **画了 `player` 忘了画 `display`**——不报错，插值白算，画面退回"逻辑帧重复出镜"的老抖动。画的是 display！
3. **对瞬移对象插值**——敌人重生那一刻被画出原地到重生点的"幽灵滑行"。
   规矩回看第四节：事件不插值。
4. **内层 while 忘写 `acc -= STEP`**——账永不还清，死循环（和坑 1 症状相同，先查这里）。
5. **`prev = player;` 忘了放在 update 动手之前**——prev 存的是"拍后"状态，
   插值退化为恒等式（画面正确但α白算），更隐蔽的是穿插多拍时中间状态被吃掉。

## 七、概念词典

| 术语 | 一句话解释 |
| --- | --- |
| 累加器（accumulator） | 记录"欠逻辑多少秒"的余额账本，攒够一拍就还一拍 |
| 固定步长（fixed timestep） | update 的固定节拍（本课 1/60 秒），正确性与确定性的地基 |
| 插值（interpolation） | prev 与 curr 的加权混合，两拍之间的脑补帧 |
| α（alpha） | `acc / STEP` ∈ [0,1)：当前时刻落在两拍之间的比例 |
| prev 快照 | 每拍开拍前的状态存档——双缓冲思想的雏形 |
| catch-up 补拍 | 掉帧/断点后一次还多拍，状态追上不丢账 |
| 死亡螺旋 | update 比 STEP 慢 → 账越欠越多；frameTime 钳制是它牢笼 |
| 确定性 | 同输入 + 固定步长 + 固定种子 = 轨迹完全可复现 |

## 八、记忆锚点 🎯

> 真实时间进账本，固定拍子还账忙；update 补拍不漂移，render 跟屏靠 α 脑补。
> prev 快照为插值，瞬移事件别混它；移动量乘 STEP 不乘 dt，
> `1.0/60.0` 带小数点——整数除法给 0，窗口当场冻住给你看。

   你修的是"判定层"还是"画面层"。

## 十二、课后答疑补录：为什么不把 update/render 塞同一处，省掉插值税？

**Q：两者同步 1:1 不就永远平滑了吗？每添一个连续运动量都要多管一个 prev/插值，很麻烦。**

这个直觉提出的方案真实存在且大量出货：同账结构（可变 dt 单循环），GameMaker
默认模式、UE 的 Tick 家族都是它；它买的是**简单**。分账结构买的是三条硬货：

1. **隧穿**：dt 保证"每秒总位移"正确，保证不了"每步不跨过敌人"——掉帧行里
   一帧 = 66 像素/步，子弹照样凭空穿过敌人。只有固定步长让**每步位移有硬上限**（结构性排除）；
2. **确定性**：同账两台机器状态轨迹分岔、bug 不可复现；固定步长 + 固定种子 = 可复现；
3. **多线程铺路**：update 不再被 Present 拴住，将来可独立线程跑（UE GameThread/RenderThread 家谱）。

**税钱的三个缓冲**：① 只有"连续运动量"（位置）配插值，事件量（颜色/瞬移）直接画当前值；
② `display` 是绘制瞬间的局部临时量，**真正的持久额外成本只有 prev 一份**；
③ 正统解是把 `{prev, curr}` + 插值公式封装成共用的小结构（下一课随 vector 登场），所有角色共用一份代码——UE 里没人手写插值，因为引擎在 Transform 层替大家交了这笔税。

判据可背走：**有高速物体？要复现 bug？** 有一条 yes 就分账。两种方案都是成熟产品线，需求定夺。
