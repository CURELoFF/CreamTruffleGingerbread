# 13 · 多态与虚函数：一个指针，多种行为

> 背景与上下文：这一课特殊——**代码你已经写完了**（GameObject 基类、
> `vector<unique_ptr<GameObject>>` 容器、虚派发的 Update/Draw），还亲手踩过了
> "双重权威"bug。所以本课不是"先学再写"，而是**武器说明书回填**：
> 把你用过的每个关键字讲到机制层，把那次 bug 立案归档成家族案例。

---

## 一、一句话核心

> **多态 = 用基类的指针/引用调用虚函数时，执行的是对象真实类型的版本。**
> 实现机制是一张虚函数表（vtable）：每个多态类一张表、每个对象头部藏一个
> 表指针——调用 = 查表 + 间接跳转（408·组成原理的"间接寻址"正用）。

## 二、三个关键词各就各位（全是你代码里的原句）

```cpp
// GameObject.hpp —— 基类：只立合同，不给实现
virtual void Update(double delta) = 0;      // 虚函数 + 纯虚
virtual void Draw(SDL_Renderer*, float) = 0;
virtual ~GameObject() = default;            // 虚析构（第四节专讲）

// EntityPlayer.hpp —— 派生类：盖章认领
void Update(double delta) override;         // override = 覆盖意图的拼写检查
```

**`virtual`**：向编译器声明"这个函数允许派生类改写，且调用时按对象真实类型分发"（第三节讲"分发"的机械层）。

**`= 0`（纯虚）**：只定合同、不给实现——于是 `GameObject` 成为**抽象类**：
编译器禁止它直接出生（`GameObject g;` 直接报错），它只能当"所有游戏对象
必须有 Update/Draw"的接口合同。为什么框架层不给默认实现？——Application
根本不该替游戏对象决定"怎么更新"，它只负责**在正确的时刻喊正确的口令**。
"合同归框架，实现归内容"——这就是你在 Run() 里写出的分层。

**`override`**：它**不改变任何行为**，是给你上的编译期保险——声明
"我确实在覆盖基类的虚函数"。若签名打错（参数类型不同），没有 override
时那行代码会**静默变成一个全新的函数**（不覆盖任何东西！），症状恰好是
"Update 从不被调、也不报错"；有 override 时编译器当场把你揪住。

## 三、虚析构：你注释里"不理解为什么存在"的那行，是承重墙

```text
你的容器存的是 GameObject*（基类指针）。
unique_ptr 析构时执行的是 delete (GameObject*)。
C++ 规则：通过基类指针 delete，若基类析构【不是 virtual】，
  → 只运行基类那半截的析构，派生类的成员（collisionRect_、将来的资源句柄）
    的死亡流程被整个跳过 → 未定义行为（资源泄漏只是最轻的症状）。

virtual ~ 的含义 = "delete 我时，按对象的真实类型找析构函数来跑"。
```

口诀：**delete 走谁的手，就运行谁的析构——virtual 把"手"换成"真身"**。
`= default` 则是 Rule of 0 的续集：内容用编译器自动合成的版本，
只额外给它盖上 virtual 戳。一行 = 整个多态容器安全的地基。

## 四、vtable：调用的机械层（408·组成原理正式挂钩）

```text
class GameObject 声明了 2 个虚函数
  → 编译器为【每个多态类】生成一张虚函数表（vtable，存于只读数据段）：
        GameObject 表：[纯虚槽位通常放"调用即报错"的哨兵，因为 = 0]
        EntityPlayer 表：[&EntityPlayer::Update, &EntityPlayer::Draw]
        EntityEnemy  表：[&EntityEnemy::Update,  &EntityEnemy::Draw]

每个多态对象的头部藏一个指针（vptr），指向自己类的表。
    e->Update(STEP) 编译后的真实动作 ≈
        沿 e 的 vptr 找到表 → 取 Update 槽位的函数地址 → 间接跳转（把 e 当 this 传入）
```

408 对照：**间接寻址 + 函数指针表**（组成原理）；**系统调用表**（OS，同族机制——
中断号查表找到处理函数，与"类型查表找到函数版本"神似）。

**成本诚实记账**：每次虚调用多一次内存读取 + 间接跳转，且阻碍内联；
每个对象多 8 字节 vptr。这些代价在游戏对象规模（千计）下不值一提，
但它们是真实的——"虚函数不是免费的，是便宜到通常不心疼"。

**这也解释了容器为什么能混装**：容器只认"表的布局"（Update 在几号槽），
完全不关心真实类型是谁——多态让"类型"从容器手中消失，只剩"能力"。

## 五、立案归档：你踩过的"双重权威"bug，正式名字叫切片家族

```text
EntityPlayer player = EntityPlayer{};                     // 栈上：原版
WorldObjects.push_back(std::make_unique<EntityPlayer>(player));
                        ↑ 复印一份放上堆 —— 从此两具身体
Update 驱动堆上的副本，Draw 画栈上的原版 → 原版纹丝不动。
```

这个家族的正式定义：**多态对象按"值"流动时发生切片（slicing）**——
把派生类对象拷给基类（赋值、按值传参、按值入容器）时，只有基类那半截
被复制，派生半截被剁掉。规矩一句话：

> **多态对象永远经指针/引用流动，禁止按值进出基类容器与函数。**

容器选型对照（这是 12 课的直接续集）：

```cpp
std::vector<GameObject> bad;      // ❌ 往里放东西时编译拒绝（抽象类不能出生）；
                                  //    即便基类不抽象，放进去的也只是被剁的基类半截
std::vector<GameObject*> risky;   // ❌ 谁负责 delete？所有权无主（02 课老朋友）
std::vector<std::unique_ptr<GameObject>> ✅   // 容器管生死
```

**unique_ptr = RAII 家族 №4（通用模板版）**：Window/Renderer 是手写的 RAII №1~3，
unique_ptr 是标准库造好的万能版——构造获取（make_unique）、析构自动 delete
（虚析构保证 delete 正确）、**禁拷贝**（所有权唯一）、**可 move**（过户）。

## 六、本次修复的两个新面孔：move 与引用别名

**`std::move(playerObj)`——所有权过户章**。unique_ptr 禁拷贝（两份指针不能
同时拥有同一个实体的寿命），要把堆上实体交给容器，只能办过户：move 之后，
原变量变成空壳（对 unique_ptr 而言标准保证它变 nullptr），堆上实体归容器。

**`EntityPlayer& player = *playerObj;`——引用别名**。`*` 解引用拿到实体本体，
用引用给它绑一个第二名字。关键问题：过户（把 unique_ptr 搬进 vector）之后
别名还有效吗？——**有效，而且永远有效**，原因值得单独记：

```text
vector 扩容搬家时，搬动的是容器里的东西 = unique_ptr 本体 = 8 字节的指针壳。
堆上的实体从未被搬动 —— 它的地址从出生到 delete 恒定不变。
所以：指针壳随便搬，别名稳如泰山。
```

这也给出**多态容器选 unique_ptr 的第二个理由**（第一个是"抽象类不能按值装"）：
**实体地址稳定**——引用别名、缓存下来的指针、其他系统持有的观察者全部安全。
（对照组：`vector<GameObject>` 搬家搬的是实体本身，所有别名瞬间全灭——
12 课"迭代器失效"的完全体形态。）

## 七、实战复盘：你的代码逐行归位

| 你写的 | 对应概念 | 状态 |
| --- | --- | --- |
| `virtual … = 0;` ×2 | 纯虚合同，抽象类 | ✅ |
| `virtual ~GameObject() = default;` | 虚析构承重墙 | ✅（本课补讲原理） |
| `… override;` ×4 | 覆盖拼写保险 | ✅ |
| `vector<unique_ptr<GameObject>>` | 多态容器（RAII №4） | ✅ 修复后 |
| `make_unique<EntityPlayer>()` | 直接堆上出生 | ✅ 修复后 |
| `std::move` 过户 + 引用别名 | 单一权威恢复 | ✅ |
| `if(e==nullptr) continue;` | 空槽残留的擦屁股代码 | 可删（容器已从 0 长起） |
| 碰撞判定走 `player`/`enemy` 别名 | 容器外的后门（暂可接受） | 挂账（将来虚化 GetRect 或 ECS） |

## 八、常见坑

1. **忘写 override 且签名打错**——静默变成新函数，"Update 永不被调"还不报错。
   规矩：**每个覆盖都写 override**，让编译器站岗；
2. **基类析构忘 virtual**——delete 基类指针 = UB。本课第三节就是它的完整病理；
3. **move 之后继续使用原变量**——unique_ptr 的 moved-from 是空壳（nullptr），
   解引用空壳 = 崩。规矩：**move 过户后，原变量只准析构或赋新值**；
4. **在构造/析构函数里调用虚函数**——此时调到的是"正在构造/析构的那一层"
   的版本，不是最派生版本（初始化顺序陷阱，先记账不展开，遇到了再上手术台）；
5. **按值装载/传参多态对象**——切片（第五节家族），一律指针/引用；
6. **给空槽写擦屁股代码**——`if(p==nullptr) continue;` 出现频繁时，先查容器
   是不是被 `vector(N)` 塞了默认空元素。

## 九、概念词典

| 术语 | 一句话解释 |
| --- | --- |
| 虚函数（virtual） | 声明"允许派生改写 + 按真实类型分发"的函数 |
| 纯虚（= 0）/ 抽象类 | 只定合同不给实现；抽象类禁止直接出生 |
| override | 覆盖意图的拼写检查器（编译期保险） |
| 虚析构 | delete 基类指针时按真实类型运行析构——多态容器的入场券 |
| vtable / vptr | 类的虚函数表 / 对象头部的表指针；调用 = 查表间接跳 |
| unique_ptr（RAII №4） | 独占所有权智能指针：禁拷贝、可 move、析构自动 delete |
| std::move | 所有权过户章；moved-from = 空壳 |
| 对象切片 | 按值把派生类拷进基类，派生半截被剁 |
| 引用别名 | `*ptr` 绑定的第二名字；实体住堆则与实体同寿 |
| 动态分发 | 运行期决定调用哪个版本（静态分发=编译期重载，对照记忆） |

## 十、记忆锚点 🎯

> 基类定合同（virtual / =0），派生盖章（override）；delete 走基类手，
> 虚析构引真身。调用即查表（vptr 一跳），容器只认槽位不认类型。
> 多态只经指针引用流，按值必切片；unique_ptr 独占禁拷贝，move 过户不留档；
> 实体住堆地址稳——vector 搬家只搬指针壳，别名稳如泰山。

## 十一、自测问题（回收后收尾模板课）

1. 派生类忘写 `override` 且把参数误写成 `void Update(float)`——编译能过吗？
   运行会怎样？为什么这个 bug 的症状恰好是"Update 似乎没被调"且**不报错**？
2. vector 扩容搬家时，容器里 unique_ptr 指向的**堆上实体**会跟着搬地址吗？
   这对"引用别名"意味着什么？如果容器改成 `vector<GameObject>`（假设可行），
   别名还能信吗？——两层都答。
3. 编译器凭什么"知道"GameObject 是抽象类、禁止 `GameObject g;`？
   （提示：`= 0` 在 vtable 里留下了什么？）
4. （组成原理视角）每个多态对象多 8 字节 vptr：一百万个对象多占多少内存？
   再算一次虚调用的额外开销：每帧 60 拍 × 1000 对象 × 每次 1 次间接跳，
   一秒钟多少次？什么时候才开始需要在意？
